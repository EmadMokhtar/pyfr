# PyFr M6 — Supply Chain Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Harden what ships and know what is in it — audited dependencies, scanned images, a software bill of materials, published multi-architecture images, automated dependency updates, log redaction, `just config-check` and seed data.

**Architecture:** Three strands. **In the service:** a redaction processor at the end of the shared structlog chain, a `config_check` module that prints the resolved settings with URL passwords and `SecretStr` values masked, and a `seed` module that creates a fixed set of orders through the HTTP API, idempotent through a state file. **Around the image:** `just audit` (pip-audit over the `uv export` of each lockfile), `just scan` and `just sbom` (Trivy, run from a compose service so its pin lives with every other one), `just build-multiarch` and `just publish-images` (buildx, `linux/amd64` and `linux/arm64`), and a runtime image with pip removed. **In CI:** a `security` job, a multi-architecture `build` job, image publishing after the version bump in `release.yml`, a nightly re-audit and re-scan, and a Dependabot configuration — with every duplicated tool and image pin collapsed into the one file Dependabot moves.

**Tech Stack:** structlog (existing), pydantic-settings (existing), httpx (existing), `pip-audit` 2.10.1 through `uvx`, Trivy 0.74.0 from `aquasec/trivy`, Docker buildx with a `docker-container` builder, GHCR (GitHub Container Registry), Dependabot (`uv`, `github-actions`, `docker`, `docker-compose`, `pre-commit` ecosystems), Commitizen 4.18.0 as a root dev dependency.

**Spec:** [`docs/superpowers/specs/2026-08-28-pyfr-cookiecutter-template-design.md`](../specs/2026-08-28-pyfr-cookiecutter-template-design.md) — section 5.1 (`just config-check`), 7.6 (redaction in the shared chain), 10.4 (the `security` and `build` rows, the release and nightly workflows), 12 (items 6 and 7, "Supply chain and security", "seed-data command"), and the M6 row of section 14. ## Global Constraints

Every task's requirements implicitly include these. The first group is inherited from M0–M5 unchanged; the rest are new in M6.

- **Python `>=3.13`.** `.python-version` contains `3.13`.
- **uv for everything Python.** `uv sync`, `uv run`, `uv lock`, `uv export`. No `pip`, no `requirements.txt` committed, no `pipx`. The one exception spec 10.4 allows arrives here: `pip-audit` runs as `uvx pip-audit`, reads a `uv export`, and never resolves anything itself (`--disable-pip --require-hashes`). It is the one pip-named tool in the project and it does not reintroduce pip as a package manager (ADR 0003).
- **Plain Python only.** M6 is the last Phase A milestone. No Jinja, no cookiecutter variables, no `{{ }}` templating anywhere. Where a value will become a template variable in M7 — the repository URL in an image label, the GHCR namespace — it is a literal here and a comment says so.
- **Package name is `reference_service`;** distribution name is `reference-service`. Service work happens under `examples/reference-service/`; workflow, Dependabot and documentation work happens at the repository root.
- **The two projects are never synced together.** The root `pyproject.toml` is the documentation and release toolchain — and, new in M6, it owns Commitizen. `examples/reference-service/pyproject.toml` is the service. A CI job runs in exactly one of them, named by `working-directory`.
- **The domain layer imports nothing but `pydantic`.** Neither new module (`config_check.py`, `seed.py`) is a layer: both sit beside `main.py` at the package root, and neither is imported by anything.
- **mypy is strict on `domain/` and `services/`,** lenient elsewhere. Write the new modules as if strict anyway.
- **Line length 88.**
- **Conventional Commits** for every commit. Commitizen reads them to decide the version; M6 makes it a root dev dependency so the version deciding the release is the version in `uv.lock`.
- **Unit tests never need Docker.** `just test` runs `tests/unit` and `tests/api` only. Every test this plan adds is a unit test.
- **`filterwarnings = ["error"]` stays.**
- **The committed contract is generated, never hand-edited.** M6 changes no endpoint. `openapi.json` must not move; the drift gate proves it.
- **A generated file is never hand-edited.** `.env.example` and the table region of `docs/reference/configuration.md` are regenerated by `just config-docs` after Task 2 adds a field.
- **A secret never reaches a log line, a traceback, an HTTP response body, or a generated document.** New in M6: nor the output of `just config-check`, whose whole purpose is to print the configuration — Task 3 masks URL passwords because `model_dump` does not (Verified Fact 7).
- **Every gate is defined in `just`, and CI calls the recipe.** The `security` job is four `just` recipes as four steps. The `build` job is one. `release.yml`'s new job is `build-images`, `scan`, `sbom`, `publish-images`. The lychee exemption stays the only one.
- **One pin per tool, in the file Dependabot moves.** New in M6, and the reason the milestone touches `.pre-commit-config.yaml`, the root `justfile`, `release.yml` and the integration tests: Dependabot has no regex manager, so a version that appears in two files drifts. Tool versions live in `uv.lock` only; container image pins live in `compose.yaml` and the two Dockerfiles only. The known remaining exceptions are listed in ADR 0014 (Task 14).
- **Exemptions expire.** A vulnerability finding is silenced only through `.trivyignore.yaml`, every entry carries a reason, a path and an `expired_at` date, and an expired entry fails the scan again (Verified Fact 4). There is no `--skip` flag and no allow-list anywhere else.
- **Scanning gates publishing.** `release.yml` scans the freshly built images before `publish-images` runs, so a fixed HIGH or CRITICAL finding blocks the push rather than following it.
- **The reference service still publishes nothing on its own version.** Images are tagged with the **repository's** version (`v0.6.0`), the same string as the git tag and the GitHub Release. One tag series — M5's decision, extended to images.

## Design

The design was settled in the brainstorming session that produced this plan. It is recorded here, not in a separate spec, following M0–M5.

### Log redaction

`observability/redaction.py` exports `REDACTED`, `DEFAULT_REDACT_FIELDS` and `make_redactor(field_names) -> Processor`. The processor is appended **last** in `_shared_processors`, so it sees the fully assembled record — everything `merge_contextvars`, the resource attributes and `dict_tracebacks` added — and, because that same list is the `foreign_pre_chain`, a value bound into context variables reaches a third-party library's record already masked. Matching is by key name: exact, case-insensitive, `-` and `_` treated alike, recursing into nested dicts and lists of dicts. Matched values become the literal string `[REDACTED]`. `LogSettings.redact_fields` (`APP_LOG__REDACT_FIELDS`, a JSON array) **replaces** the default list. Stated limitation: key-name matching cannot see a secret interpolated into a message string; `SecretStr` and `load_settings`'s `include_input=False` cover the two ways a secret enters our own records as a value.

### `just config-check`

`reference_service/config_check.py`, run as `python -m reference_service.config_check`, in the package rather than `scripts/` so it also runs inside the image (`docker compose run --rm app python -m reference_service.config_check` — a runbook entry). It calls `load_settings()`, so a malformed environment exits 78 with the same readable message the service prints at startup; a valid one prints the settings as one pretty-printed JSON object. Masking has two layers: `model_dump(mode="json")` renders every `SecretStr` as `**********`; then a walker blanks the password component of any string value that parses as a URL carrying credentials, because `APP_DATABASE__DSN` and `APP_CACHE__DSN` otherwise print their passwords (Verified Fact 7). Generic, so a future DSN field cannot forget to opt in. Not part of `just check` — it is a tool, not a gate.

### Seed data

`reference_service/seed.py`, run as `python -m reference_service.seed --base-url URL --state PATH`, in the package because the compose one-shot runs it from the `app` image. It POSTs five fixed orders through the HTTP API with plain dicts (no `api.v1.schemas` import — it is a client), GETs each order's receipt once so the receipt store has objects too, and prints `key  order_id  total  created|exists`. Idempotency uses a state file mapping seed key to the server-assigned id: on each run every recorded id is checked with a GET; 200 skips, 404 (the database was wiped) re-creates. `just seed` runs it against `localhost:${APP_HTTP_PORT}` with `.seed-state.json` (ignored by git). Compose gains a `seed` one-shot on the `app` image with `depends_on: app: condition: service_healthy` and the state in a named volume, so `just up` alone yields data and `just down` clears it with the database. No order totals `999.99`, the WireMock stub's decline trigger.

### Dependency and image security

`just audit` — `uv export --frozen --all-groups` piped into `uvx pip-audit==2.10.1 --requirement /dev/stdin --disable-pip --require-hashes --strict`; the same recipe at the repository root for the docs toolchain's lock. `just scan` — Trivy over both images with `--severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 --scanners vuln,secret`, exemptions only through `.trivyignore.yaml` with expiry dates. `just sbom` — `trivy image --format cyclonedx` per image into `sbom/`. Trivy runs as a compose service under the `tools` profile so its image pin sits in `compose.yaml` with every other one. The runtime image drops pip, which is the only source of HIGH findings in the application image today (Verified Fact 5); the migrations base moves to `migrate/migrate:v4.20.1`, and the five findings its newest release still carries are exempted with a reason and a 90-day expiry (Verified Fact 6).

### Multi-architecture builds and publishing

`just build-multiarch` builds both Dockerfiles for `linux/amd64,linux/arm64` on a `docker-container` builder named `pyfr` with no output — proof that both architectures build. `just publish-images version registry builder` does the same with `--push`, tags `<version>` and `latest`, and OCI labels for version and revision; the `org.opencontainers.image.source` label is static in each Dockerfile, because it is what makes GHCR link a package to this repository. `release.yml` gains a `publish-images` job that builds, scans, produces the SBOMs, pushes, and attaches the SBOMs to the GitHub Release. Images: `ghcr.io/emadmokhtar/pyfr-reference-service` and `ghcr.io/emadmokhtar/pyfr-reference-service-migrations`.

### Dependabot, and one pin per tool

`.github/dependabot.yml`: weekly, one grouped PR per ecosystem, Conventional Commit prefixes, and the `no-docs-needed` label so the docs-freshness gate does not fail dependency PRs. Because Dependabot cannot update a version literal inside a `justfile` or a workflow, the duplicates are removed: the `ruff`, `uv-lock` and `commitizen` pre-commit hooks become `repo: local` hooks that run the lock-pinned tools; Commitizen becomes a root dev dependency called through `uv run --locked --group dev cz` in the root `justfile` and `release.yml`; the integration tests read their container image names from `compose.yaml` and the `FROM` line of `Dockerfile.migrations`; `o11y-gates` reads the `lgtm` image from `docker compose config`.

### Documentation

Four ADRs (0013 redaction, 0014 Dependabot and one pin per tool, 0015 publish on release under the repository version, 0016 scan policy and expiring exemptions). A new `docs/reference/supply-chain.md`. Additions to `logging.md`, `runbook.md`, `contributing.md`, `getting-started.md`, `reference/commands.md`, `guides/run-in-a-container.md`, `glossary.md`, both READMEs, and `roadmap.md`.

## What M6 deliberately does not include

| Left out | Reason |
|---|---|
| A distroless runtime base | Spec 12's "no shell tools in the final stage" is not taken. There is no maintained, freely tag-pinnable Python 3.13 distroless image, and the `CMD` needs `sh` to expand `APP_HTTP_PORT`. Removing pip (Task 5) is what the scan actually asked for; Trivy over the slim base is the standing mitigation |
| Renovate | User decision, recorded in ADR 0014. Dependabot covers every ecosystem this repository has; what it cannot do — update a literal inside a `justfile` — is answered by not having such literals |
| Image signing (cosign) and SLSA provenance attestations | Not in the spec. A natural follow-on now that images are published; unscheduled, not decided against |
| A list-orders endpoint, to make the seed idempotent through the API | A contract change (drift gate, breaking-change gate, baseline) for a development tool. The state file does the job |
| `pip-audit` as a pre-commit hook | A network call on every commit breaks spec 10.5's two-second budget |
| Redacting secrets inside message strings, or regex scanning of values | Spec 7.6 says key names. Value scanning is a different, noisier tool with its own false-positive budget |
| Native arm64 runners for the multi-architecture build | QEMU emulation built the application image for both platforms in 12 seconds on a cold builder (Verified Fact 8). Revisit only if that becomes measurably slow |
| Scanning the pushed image in `release.yml` | The freshly built amd64 images are scanned **before** the push. Same commit, same lockfile, same Debian package versions; the arm64 image differs only in architecture. Scanning after the push would need registry credentials passed into the Trivy container for a package that is private until made public, for no additional information |
| `--load`ing the multi-architecture build locally | A `docker-container` builder cannot load a two-platform image into the daemon; `just build-images` stays the single-architecture path that `scan` and `sbom` consume |
| Deleting `ensurepip`'s bundled pip wheel from the runtime image | Trivy does not flag it (Verified Fact 5); removing it would be hardening theatre |
| A Dependabot `pip` entry for the root project | The root project has no `requirements.txt`; `uv` is its ecosystem |
| Re-recording the nightly `scan` against the `latest` tag before the first M6 release exists | The tag appears with the first release after this milestone merges. Until then that nightly step fails on "image not found"; Task 13 documents this as expected for one night at most |

## Verified Facts

Each was established by running the installed tools, not assumed. They exist so the implementer does not rediscover them.

**1. `pip-audit` 2.10.1 audits a `uv export` without pip and without resolving.**

```
uv export --frozen --format requirements.txt --no-emit-project \
  | uvx pip-audit==2.10.1 --requirement /dev/stdin --disable-pip --require-hashes --strict --progress-spinner off
```

exits 0 with `No known vulnerabilities found` for both lockfiles (2 221 lines for the service). `--require-hashes` is what lets `--disable-pip` work without `--no-deps`: `uv export` emits `--hash` lines for every pin, and pip-audit accepts a fully hashed file as needing no resolution. Without `--require-hashes`, `--no-deps` is needed instead and pip-audit prints a warning about unhashed pins on every run.

**2. The default Docker Desktop builder cannot build two platforms at once.**

`docker buildx build --platform linux/amd64,linux/arm64 .` on the `desktop-linux` builder fails with `Multi-platform build is not supported for the docker driver. Switch to a different driver, or turn on the containerd image store`. A builder created with `docker buildx create --name pyfr --driver docker-container` builds both — with no output, or with `--push`. It cannot `--load` a two-platform result into the daemon.

**3. Trivy 0.74.0 from its own image scans a locally built image over the Docker socket, and writes CycloneDX 1.7.**

```
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v trivy-cache:/root/.cache/trivy \
  aquasec/trivy:0.74.0 image --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 \
  --scanners vuln,secret --no-progress reference-service:ci
```

works with no Trivy installed on the host. `--format cyclonedx --output /out/x.cdx.json` produced a 255 KB document, `bomFormat: CycloneDX`, `specVersion: 1.7`, 161 components including `libc6`, `openssl`, `fastapi`, `pydantic`, `uvicorn`. The first run downloads the vulnerability database (about a minute); the named volume makes later runs take seconds.

**4. `.trivyignore.yaml` entries with `expired_at` behave exactly as the policy needs.**

With five entries covering every finding in `migrate/migrate:latest`, one carrying `expired_at: 2026-01-01` (in the past), the scan failed on exactly that one finding, exit 1. With all five dated in the future, exit 0 and `Some vulnerabilities have been ignored/suppressed`. The file is passed as `--ignorefile /path`. Entries take `id`, `paths` (a list), `statement`, `expired_at`.

**5. Both HIGH findings in today's application image are pip's, and removing pip removes them.**

`reference-service:ci` scans to `Total: 2 (HIGH: 2, CRITICAL: 0)`, Debian layer `0`: `msgpack 1.1.2` (GHSA-6v7p-g79w-8964) and `setuptools 70.3.0` (CVE-2025-47273). Neither is in `uv.lock`. Both live at `/usr/local/lib/python3.13/site-packages/pip/_vendor/`, shipped by `python:3.13-slim-trixie`. A throwaway image built `FROM reference-service:ci` with `RUN /usr/local/bin/python -m pip uninstall -y pip` scans to exit 0. The full path matters: `/app/.venv/bin` is first on `PATH`, and the venv's `python` has no pip to uninstall (`No module named pip`). `ensurepip` still reports version 26.2.1 afterwards — its bundled wheel is not something Trivy flags.

**6. The migrations base has 48 fixed HIGH/CRITICAL findings at v4.19.0 and 5 at the newest release.**

`reference-service-migrations:ci` (`migrate/migrate:v4.19.0`, alpine 3.19.8): 2 in `musl` (OS layer) and 46 in the Go binary, including a CRITICAL in `github.com/jackc/pgx/v5 v5.5.4`. `migrate/migrate:latest` (v4.20.1, published 2026-09-09, alpine 3.24.1): OS layer 0, Go binary 5 HIGH — `golang.org/x/crypto v0.53.0` (CVE-2026-56854, ssh), `golang.org/x/text v0.38.0` (CVE-2026-56852), `google.golang.org/grpc v1.82.0` (CVE-2026-84304, CVE-2026-84445, GHSA-hrxh-6v49-42gf — xDS). None is reachable from `migrate up` against PostgreSQL, none is fixable here, and no `.trivyignore.yaml`-free gate can be green on that image. Task 7 exempts exactly these five, each with a 90-day expiry.

**7. `model_dump(mode="json")` masks `SecretStr` but prints URL passwords in clear.**

With `APP_DATABASE__DSN=postgresql://app:s3cr3t@db:5432/app` and `APP_CACHE__DSN=redis://:r3d1s@cache:6379/0`, the dump contains `s3cr3t` and `r3d1s` verbatim, while `api_key` and `secret_access_key` render as `**********`. Task 3's URL walker exists because of this.

**8. A cold `docker-container` builder built both platforms of both images in 15 seconds total.**

Migrations image 3 s, application image 12 s, `linux/amd64` and `linux/arm64` both present in the log, on an Apple Silicon host where amd64 is the emulated side. Every dependency in the lock has an arm64 wheel; nothing compiled from source. Base images `ghcr.io/astral-sh/uv:0.11-python3.13-trixie-slim`, `python:3.13-slim-trixie` and `migrate/migrate` all publish both platforms.

**9. A multi-architecture `--push` assembles an OCI image index, rehearsed against a local registry.**

`registry:3` on `localhost:5001`, a builder created with `--driver-opt network=host --config buildkitd.toml` (`[registry."localhost:5001"] http = true`), then `docker buildx build --platform linux/amd64,linux/arm64 --push -t localhost:5001/pyfr-reference-service-migrations:0.0.0-rehearsal ...` exited 0 and `docker buildx imagetools inspect` showed `application/vnd.oci.image.index.v1+json` with one manifest per platform. Port 5000 is taken on this machine; the rehearsal uses 5001.

**10. Dependabot supports every ecosystem this repository has, and matches `Dockerfile.migrations`.**

`uv` (general availability March 2025), `github-actions`, `docker`, `docker-compose` and `pre-commit` are all `package-ecosystem` values; `directories:` takes a list; `groups`, `commit-message.prefix` and `labels` exist. The docker file fetcher's rule is `/dockerfile|containerfile/i` matched anywhere in the filename, so `Dockerfile.migrations` is found.

**11. pre-commit runs hooks from the repository root with root-relative paths, even when invoked from `examples/reference-service/`.**

A throwaway `repo: local` hook printed `cwd=<repo root> args=examples/reference-service/src/reference_service/main.py`. So a local ruff hook must use `uv run --project examples/reference-service` — which selects that project's environment **without** changing directory — not `--directory`, which would chdir and break the paths. Four local hooks (`ruff check`, `ruff format --check`, `uv lock --check` twice) over every tracked file ran in 0.5 s.

**12. Commitizen as a root dev dependency works through `uv run --locked --group dev cz`, including `cz bump`.**

In a scratch copy of the root project: `uv add --group dev "commitizen==4.18.0"`, then `uv run --locked --group dev cz version --project` printed `0.5.0`. In a scratch git repository tagged `v0.5.0` with one `feat:` commit, `uv run --locked --group dev cz bump --yes --changelog` bumped to 0.6.0, tagged `v0.6.0`, updated both `pyproject.toml` and the lock's `[[package]] name = "pyfr"` entry, left a clean tree, and the next `--locked` call still passed. With the lock deliberately stale, `--locked` refused with `The lockfile at uv.lock needs to be updated` — nothing was written.

**13. `just`'s dotenv loader strips double quotes out of an unquoted value; single quotes survive both loaders.**

`APP_X=["access_token","api_key"]` in `.env` reaches a recipe as `APP_X=[access_token,api_key]` — no longer JSON. `APP_X='["access_token","api_key"]'` reaches the recipe intact and python-dotenv/pydantic-settings parse it to `frozenset({'access_token', 'api_key'})`. Today's `.env.example` line `APP_LOG__LEVELS={}` only works because `{}` contains no quotes. Task 2 makes the generator single-quote every JSON default.

**14. The compose file already pins every image the tests pin, to the same versions.**

`postgres:16-alpine`, `redis:8-alpine`, `minio/minio:RELEASE.2025-09-07T16-13-09Z`, `grafana/otel-lgtm:0.32.1` in `compose.yaml` match `tests/integration/conftest.py` and `test_observability_stack.py`; `migrate/migrate:v4.19.0` in `Dockerfile.migrations` matches `MIGRATE_IMAGE`. Task 10's loader starts green. `ruff 0.16.5` in `uv.lock` matches the pre-commit rev `v0.16.5`; `commitizen==4.18.0` appears in `.pre-commit-config.yaml`, three times in `release.yml` and twice in the root `justfile`.

**15. Order ids are server-generated, there is no list endpoint, and `TestClient` is an `httpx.Client`.**

`POST /api/v1/orders` returns 201 with `id` and `total: {"amount": "37.00", "currency": "EUR"}`; `GET /api/v1/orders/{id}` and `GET /api/v1/orders/{id}/receipt` exist; nothing lists orders. `fastapi.testclient.TestClient` subclasses `httpx.Client`, so `seed(client, state_path)` typed against `httpx.Client` is exercised by the existing `client` fixture with no server. The WireMock stub declines an authorisation whose `amount` is `999.99` and authorises everything else.

**16. `observability/__init__.py` is empty, so `settings.py` can import `observability.redaction` without a cycle.**

`otel.py` imports `settings`; `redaction.py` imports only `structlog.types`. PyYAML is already a direct dev dependency of the service (for the SLO rule tests), so Task 10 adds no dependency.

### Task 1: The redaction processor, last in the shared chain

**Files:**
- Create: `examples/reference-service/src/reference_service/observability/redaction.py`
- Create: `examples/reference-service/tests/unit/test_redaction.py`

**Interfaces:**
- Produces: `REDACTED: str = "[REDACTED]"`, `DEFAULT_REDACT_FIELDS: frozenset[str]`, `make_redactor(field_names: Collection[str]) -> structlog.types.Processor`; `configure_logging(..., redact_fields: Collection[str] = DEFAULT_REDACT_FIELDS)`.

- [ ] **Step 1: Write the failing tests**

`examples/reference-service/tests/unit/test_redaction.py`:

```python
"""Redaction sits in the SHARED processor chain, so it covers every record
however it was produced — a structlog call, a value bound into context
variables by middleware, or a standard-library record from a third-party
library — at every depth of nesting. These tests go through
configure_logging and read the rendered output, because
structlog.testing.capture_logs bypasses the processors entirely.
"""

import json
import logging
import string
from collections.abc import Callable, Iterator

import pytest
import structlog
```

```python
"""Mask secret-bearing fields before a record is rendered.

A processor in the SHARED chain (observability/logging.py), not a
call-site responsibility: it runs on every record however it was
produced — a structlog call, a value bound into context variables by
middleware, or a standard-library record bridged from a third-party
library through `foreign_pre_chain` — so a `password` cannot reach the
log backend because one call site forgot (spec 7.6, spec 12 item 6).

Matching is by KEY NAME only: exact, case-insensitive, `-` and `_`
treated alike, at any depth of nested dicts and lists. It does not scan
string values. A secret interpolated into a message string is not
something a key-name rule can see, and spec 7.6 asks for key names; the
two other ways a secret enters our own records as a value —
`SecretStr`'s representation and `load_settings`'s `include_input=False`
— are already closed in settings.py.
"""

from __future__ import annotations

from collections.abc import Collection, MutableMapping
from typing import Any

from structlog.types import Processor

REDACTED = "[REDACTED]"

# Replaced, not extended, by APP_LOG__REDACT_FIELDS (settings.py): one rule
# for what the effective list is, with no hidden merge to reason about.
DEFAULT_REDACT_FIELDS: frozenset[str] = frozenset(
    {
        "password",
        "passwd",
        "secret",
        "secret_key",
        "secret_access_key",
        "token",
        "access_token",
        "refresh_token",
        "api_key",
        "apikey",
        "authorization",
        "cookie",
        "set_cookie",
        "card_number",
        "cvv",
    }
)


def _normalise(key: str) -> str:
    return key.replace("-", "_").lower()


def _redact_value(value: Any, names: frozenset[str]) -> Any:
    """Return `value` with every matching key at any depth masked."""
    if isinstance(value, dict):
        return {
            key: (
                REDACTED
                if isinstance(key, str) and _normalise(key) in names
                else _redact_value(item, names)
            )
            for key, item in value.items()
        }
    if isinstance(value, list):
        return [_redact_value(item, names) for item in value]
    return value


def make_redactor(field_names: Collection[str]) -> Processor:
    """A structlog processor masking every configured field name."""
    names = frozenset(_normalise(name) for name in field_names)

    def redact_sensitive_fields(
        logger: Any, method_name: str, event_dict: MutableMapping[str, Any]
    ) -> MutableMapping[str, Any]:
        for key in list(event_dict):
            if _normalise(key) in names:
                event_dict[key] = REDACTED
            else:
                event_dict[key] = _redact_value(event_dict[key], names)
        return event_dict

    return redact_sensitive_fields
```

```python
"""Print the resolved configuration with every secret masked.

    just config-check
    docker compose run --rm app python -m reference_service.config_check

Loads settings exactly as the service does at startup, so a malformed
environment exits with the same readable message and the same exit code
(78, EX_CONFIG) -- which makes this the thing to run when the service
will not start (docs/runbook.md). A valid environment prints one JSON
object, keys sorted.

Two layers of masking. `model_dump(mode="json")` renders every
`SecretStr` as `**********`. That is not enough on its own (M6 plan,
Verified Fact 7): `APP_DATABASE__DSN` and `APP_CACHE__DSN` are URL
types, and a URL's password is plain text inside the dumped string.
`mask` walks the dump and blanks the password of any string that parses
as a URL carrying credentials -- generic, so a DSN field added later is
covered without opting in.
"""

from __future__ import annotations

import json
import sys
from typing import Any
from urllib.parse import urlsplit, urlunsplit

from reference_service.settings import Settings, load_settings

# The same string pydantic prints for a SecretStr, so the output reads as
# one convention rather than two.
MASK = "**********"


def mask_url_credentials(value: str) -> str:
    """Blank the password of a URL that carries one; anything else unchanged.

    Works on the netloc as text rather than through `.hostname`/`.port`,
    which lower-case the host, strip IPv6 brackets and raise on a bad
    port -- this must print what is configured, only with the password
    removed.
    """
    try:
        parts = urlsplit(value)
    except ValueError:
        return value
    credentials, at, host_port = parts.netloc.rpartition("@")
    if not at or ":" not in credentials:
        return value
    user, _, _ = credentials.partition(":")
    return urlunsplit(parts._replace(netloc=f"{user}:{MASK}@{host_port}"))


def mask(value: Any) -> Any:
    """Apply `mask_url_credentials` to every string at any depth."""
    if isinstance(value, dict):
        return {key: mask(item) for key, item in value.items()}
    if isinstance(value, list):
        return [mask(item) for item in value]
    if isinstance(value, str):
        return mask_url_credentials(value)
    return value


def resolved_configuration(settings: Settings) -> dict[str, Any]:
    dumped: dict[str, Any] = settings.model_dump(mode="json")
    masked: dict[str, Any] = mask(dumped)
    return masked


def main(env_file: str | None = ".env") -> int:
    # Exits 78 with a readable, value-free message when the environment
    # is invalid -- see load_settings.
    settings = load_settings(env_file=env_file)
    print(json.dumps(resolved_configuration(settings), indent=2, sort_keys=True))
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

```python
"""Seed a running service with a fixed set of orders.

    just seed                      # against localhost; state in .seed-state.json
    docker compose run --rm seed   # what `just up` runs once `app` is healthy

Goes through the HTTP API on purpose: it works against every backend
combination the same way, it exercises the real request path (payment
authorisation included), and it depends on nothing but the published
contract. Plain dicts rather than the API's Pydantic schemas for the same
reason -- this is a client.

Idempotent through a state file rather than through the API, because
order ids are server-generated and there is no list endpoint (adding one
for a development tool would be a contract change). The file maps each
seed key to the id the service assigned. On every run each recorded id
is checked with a GET and re-created only when it is gone -- which is
what happens after `just down` wipes the database but not the file.
"""

from __future__ import annotations

import argparse
import json
import sys
from pathlib import Path
from typing import Any, NamedTuple

import httpx

ORDERS_PATH = "/api/v1/orders"

# Deterministic on purpose: the same customers and lines every time, so
# the documentation can name them. No order totals 999.99 -- that amount
# is what the WireMock payment stub (ops/payment-stub/mappings/decline.json)
# declines, and a seed that fails on `just up` is worse than none.
SEED_ORDERS: dict[str, dict[str, Any]] = {
    "espresso-beans": {
        "customer_id": "0f1d2c3b-4a59-4e6f-8a7b-9c0d1e2f3a4b",
        "lines": [
            {"sku": "beans-1kg", "quantity": 2, "unit_amount": "18.50", "currency": "EUR"}
        ],
    },
    "filter-papers": {
        "customer_id": "0f1d2c3b-4a59-4e6f-8a7b-9c0d1e2f3a4b",
        "lines": [
            {"sku": "filter-100", "quantity": 3, "unit_amount": "4.25", "currency": "EUR"}
        ],
    },
    "grinder": {
        "customer_id": "7e6d5c4b-3a29-4180-9f8e-7d6c5b4a3928",
        "lines": [
            {"sku": "grinder-pro", "quantity": 1, "unit_amount": "249.00", "currency": "EUR"}
        ],
    },
    "mixed-basket": {
        "customer_id": "7e6d5c4b-3a29-4180-9f8e-7d6c5b4a3928",
        "lines": [
            {"sku": "mug-ceramic", "quantity": 4, "unit_amount": "9.90", "currency": "EUR"},
            {"sku": "spoon-set", "quantity": 1, "unit_amount": "12.40", "currency": "EUR"},
        ],
    },
    "bulk-order": {
        "customer_id": "c1b2a394-8576-4e6f-a0b1-c2d3e4f5a6b7",
        "lines": [
            {"sku": "beans-1kg", "quantity": 25, "unit_amount": "18.50", "currency": "USD"}
        ],
    },
}


class SeededOrder(NamedTuple):
    key: str
    order_id: str
    total: str
    created: bool


class SeedError(RuntimeError):
    """The service rejected a request. Orders already created stay created."""


def _load_state(path: Path) -> dict[str, str]:
    if not path.exists():
        return {}
    data = json.loads(path.read_text(encoding="utf-8"))
    return {str(key): str(value) for key, value in data.get("orders", {}).items()}


def _save_state(path: Path, orders: dict[str, str]) -> None:
    path.write_text(
        json.dumps({"orders": orders}, indent=2, sort_keys=True) + "\n",
        encoding="utf-8",
    )


def _money(total: dict[str, Any]) -> str:
    return f"{total['amount']} {total['currency']}"


def seed(client: httpx.Client, state_path: Path) -> list[SeededOrder]:
    """Create every seed order that does not already exist; report them all."""
    known = _load_state(state_path)
    result: list[SeededOrder] = []
    for key, payload in SEED_ORDERS.items():
        order_id = known.get(key)
        if order_id is not None:
            existing = client.get(f"{ORDERS_PATH}/{order_id}")
            if existing.status_code == 200:
                total = _money(existing.json()["total"])
                result.append(SeededOrder(key, order_id, total, created=False))
                continue
            if existing.status_code != 404:
                raise SeedError(
                    f"GET {ORDERS_PATH}/{order_id} returned {existing.status_code}"
                )

        created = client.post(ORDERS_PATH, json=payload)
        if created.status_code != 201:
            raise SeedError(
                f"POST {ORDERS_PATH} for {key!r} returned "
                f"{created.status_code}: {created.text}"
            )
        body = created.json()
        order_id = str(body["id"])

        # Once, so the receipt store holds an object per seeded order too.
        receipt = client.get(f"{ORDERS_PATH}/{order_id}/receipt")
        if receipt.status_code != 200:
            raise SeedError(
                f"GET {ORDERS_PATH}/{order_id}/receipt returned {receipt.status_code}"
            )

        # Saved after EACH order, not at the end: a failure on the fourth
        # order must not lose the three ids already issued.
        known[key] = order_id
        _save_state(state_path, known)
        result.append(SeededOrder(key, order_id, _money(body["total"]), created=True))
    return result


def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(
        description="Seed a running reference service with a fixed set of orders."
    )
    parser.add_argument("--base-url", default="http://localhost:8000")
    parser.add_argument("--state", type=Path, default=Path(".seed-state.json"))
    args = parser.parse_args(argv)

    with httpx.Client(base_url=args.base_url, timeout=10.0) as client:
        try:
            seeded = seed(client, args.state)
        except (SeedError, httpx.HTTPError) as exc:
            print(f"seed failed: {exc}", file=sys.stderr)
            return 1

    width = max(len(order.key) for order in seeded)
    for order in seeded:
        state = "created" if order.created else "exists"
        print(f"{order.key:<{width}}  {order.order_id}  {order.total:>12}  {state}")
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

```python
"""Image pins come from compose.yaml and the Dockerfiles, and only from there.

Before M6 the integration tests carried their own copies of every image
tag, each with a comment saying "pinned to the same version compose
uses". Dependabot updates compose.yaml and the Dockerfiles; it cannot
update a string literal in a test. Reading the pins from the files it
DOES update is what turns "CI runs the versions a developer runs" from a
comment into a property (ADR 0014).
"""

from __future__ import annotations

import re
from pathlib import Path

import yaml

PROJECT_ROOT = Path(__file__).resolve().parents[1]
COMPOSE_FILE = PROJECT_ROOT / "compose.yaml"
DOCKERFILE_MIGRATIONS = PROJECT_ROOT / "Dockerfile.migrations"


def compose_image(service: str) -> str:
    """The `image:` of one compose service, as written."""
    services = yaml.safe_load(COMPOSE_FILE.read_text(encoding="utf-8"))["services"]
    return str(services[service]["image"])


def dockerfile_base_image(dockerfile: Path = DOCKERFILE_MIGRATIONS) -> str:
    """The image named by the first `FROM` line."""
    for line in dockerfile.read_text(encoding="utf-8").splitlines():
        match = re.match(r"^FROM\s+(\S+)", line)
        if match:
            return match.group(1)
    raise ValueError(f"no FROM line in {dockerfile}")
```

- [ ] **Step 1: ADR 0013 — Redact by key name, in the shared processor chain**

**Context.** Spec 7.6 and spec 12 item 6 ask that a `password` or `card_number` cannot reach the log backend by accident, including from third-party libraries. Three designs were possible: each call site masks what it logs; a processor in structlog's chain masks by field name; a filter scans every rendered string for secret-shaped values.

**Decision.** We mask by key name, in one processor appended **last** to the shared chain in `observability/logging.py`, so it sees the fully assembled record — bound context included — and, because the same list is the standard-library `foreign_pre_chain`, third-party records too. Matching is exact, case-insensitive, `-` and `_` alike, at any depth. The list is `APP_LOG__REDACT_FIELDS`, which replaces the default rather than extending it.

**Alternatives.** Call-site masking: the one place it is forgotten is the one that matters. Value scanning: needs a regex per secret shape, produces false positives on ordinary hexadecimal identifiers, and still cannot tell a token from a trace id. Extending the default list instead of replacing it: two sources for one setting, and no way to *remove* a default that collides with a legitimate field name.

**Consequences.** A field named `token` is always masked, even when it is a pagination token — rename the field or configure the list. A secret interpolated into a message string is **not** covered; `SecretStr` and `load_settings`'s `include_input=False` close the two value-shaped holes in our own code, and the limitation is documented in `docs/reference/logging.md`.

- [ ] **Step 2: ADR 0014 — Dependabot, and one pin per tool**

**Context.** Spec 12 names Renovate. This repository already had pinned tool revisions in `.pre-commit-config.yaml` drifting behind `uv.lock`, and M5 pinned Commitizen in two files with a comment saying the copies must be kept equal by hand. Renovate's regex manager can rewrite a version literal anywhere; Dependabot cannot, but is GitHub-native, needs no installation, and supports every ecosystem here: `uv`, `github-actions`, `docker`, `docker-compose`, `pre-commit`.

**Decision.** We use Dependabot, and we remove every duplicated pin rather than policing it. Tool versions live in `uv.lock` only: the ruff, uv-lock and Commitizen pre-commit hooks are `repo: local` hooks that run the locked tools; Commitizen is a root dev dependency called through `uv run --locked --group dev cz` by the root `justfile` and `release.yml`. Container image pins live in `compose.yaml` and the two Dockerfiles only: the integration tests read them from there, and so does `just o11y-gates`.

**Alternatives.** Renovate (hosted app or self-hosted action): more capable, one more thing to install and, self-hosted, a credential to keep alive. A "pins agree" gate over the duplicates: every Dependabot PR that bumped one copy would be red until a human bumped the other — the drift problem with extra steps.

**Consequences.** Two version literals remain outside Dependabot's reach and are accepted knowingly: `pip-audit==2.10.1` in both justfiles (its advisory data is fetched live, so a stale binary still reports new findings), and the `oasdiff` image pinned in `scripts/check_contract_compatibility.py` (pre-existing). The ruff hooks carry `--project examples/reference-service` until M7 makes the service standalone. Dependabot PRs carry `no-docs-needed`.

- [ ] **Step 3: ADR 0015 — Publish images on release, under the repository's version**

**Context.** M5 decided the repository has one version, one changelog and one tag series, and that the reference service publishes nothing. M6 adds a registry. The images could be tagged with the service's own `0.1.0`, pushed on every merge, or pushed on release under the repository's tag.

**Decision.** `release.yml` pushes `ghcr.io/emadmokhtar/pyfr-reference-service` and `…-migrations`, for `linux/amd64` and `linux/arm64`, tagged with the release's `vX.Y.Z` and `latest`, after `scan` has passed on the same commit's images. Nothing is pushed from pull requests or from merges that do not release. The `org.opencontainers.image.source` label links each package to this repository.

**Alternatives.** Never publish: nothing for the SBOM to describe, nothing for the nightly scan to re-check, and M7 would have no release path to templatise. Publish on every merge: registry churn for images nothing consumes continuously. Tag with the service's version: a second version series, which M5 rejected.

**Consequences.** The first push creates private packages; a one-time repository setting makes them public. The registry namespace is a literal until M7. `latest` moves with every release, which is what the nightly scan wants and what a deployment should never pin.

- [ ] **Step 4: ADR 0016 — Scans fail on fixed HIGH and CRITICAL findings, and every exemption expires**

**Context.** Spec 12 says Trivy fails on high-severity findings. Two facts complicate that: a finding with no available fix is nothing a pull request can act on, and the newest `migrate/migrate` release carries five HIGH findings in code paths `migrate up` never executes, with no fix in any release. A gate that is red forever is a gate people stop reading.

**Decision.** `just scan` runs Trivy with `--severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 --scanners vuln,secret` over both images. A finding is exempted only through `.trivyignore.yaml`, where every entry names the vulnerability, the path it applies to, a reason, and an `expired_at` date about ninety days out; an expired entry fails the scan again. There is no other allow-list and no skip flag in any recipe or workflow.

**Alternatives.** Fail on everything including unfixed: permanently red on any Debian base. Scan only our own layers: would have hidden v4.19.0's CRITICAL in `pgx`. Exemptions without expiry: the list only ever grows.

**Consequences.** Someone must renew or drop five entries by 2026-12-10; a Dependabot bump of the migrate base is the natural moment. `--ignore-unfixed` means unfixed findings are visible in the output but never fail the build — read the table, not just the exit code.
